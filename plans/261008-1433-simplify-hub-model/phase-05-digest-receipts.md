# Phase 5: Digest-Only Receipts (D8, S4)

## Overview

This phase eliminates the duplicate file-body object database in `history/operations/` (D8, Red Team S4). Operation receipts retain only cryptographic digests and audit metadata: operation ID, idempotency key, request digest, catalog snapshots, and per-path before/after digests.

File bodies and unified diffs for committed changes are reconstructed directly from Git history. Workspace schema version is bumped from 4 to 5 via a registered WAL migration step (`planV4ToV5`) that strips bodies from legacy receipts, dramatically reducing repository footprint (reducing the live hub's 208 KB receipt to ~3 KB).

## Git-First Diff and Undo Capabilities

### 1. Committed Operations
When an operation has been committed to Git:
- **Receipt Commit:** Git commit `H` that introduced or touched the receipt is identified via `git log -n 1 --format=%H -- <receipt_path>`.
- **Before Content:** Retrieved via `git show H~1:<path>` (or empty string if newly created in `H`).
- **After Content:** Retrieved via `git show H:<path>` (or empty string if deleted in `H`).
- **Diff:** Generated via `git diff H~1..H -- <path>` or bounded unified diff of before/after contents.
- **Undo:** Full compensating checkout or revert is supported via standard Git tools: `git revert <commit>` or `git checkout <commit>~1 -- <path>`.

### 2. Uncommitted Operations
When an operation has been applied to the workspace working tree but not yet committed:
- **What Undo CAN Still Do:**
  - If `headDigest == stored.BeforeDigest`: Git HEAD holds the exact before-image. Undo is completely safe and verifiable via `git checkout HEAD -- <path>`.
  - If `stored.BeforeDigest == ""` and the file is untracked: the file was newly created by the operation. Undo is completely safe by removing the file (`rm <path>`).
  - `workspace_diff`: retrieves the before-image from `HEAD:<path>` and compares it against current worktree bytes, rendering the full diff with `diff_available: true`.
- **What Undo CANNOT Do Without Bodies:**
  - If the file had uncommitted local modifications prior to the operation (`headDigest != stored.BeforeDigest`), the intermediate uncommitted before-state cannot be reconstructed without file bodies because it was never committed to Git object storage. In this case, `GetOperationDiff` labels the change `digest_only_metadata: true` and warns that no automatic direct restore can be established.

## Backward Compatibility & Migration Decision

- **Receipt Loader:** The receipt parser in `internal/app/operations.go` and `internal/mutation/` preserves optional unmarshaling of legacy receipt fields (`before_content`, `after_content`, `content_available`). Older receipts continue to load transparently.
- **WAL Migration (`planV4ToV5`, Schema Version 5):**
  - We choose to implement WAL migration step `planV4ToV5` that strips embedded body fields from existing on-disk receipts in `history/operations/`.
  - **Reasoning:** Storing file bodies in receipt files bloats the Git repository unnecessarily (e.g. 208 KB for a single operation in the live hub). Stripping these bodies permanently shrinks operations storage by over 90% without breaking any contract or losing audit history.
  - The live hub's 208 KB receipt (`OP-c011d730fa8122171101881543a63bc8.yaml`) serves as the primary integration fixture.

## Acceptance Criteria

1. New receipts generated by `mutation.ConfirmMutation` store digests only (`path`, `before`, `after`) and omit body fields.
2. Older receipts with embedded bodies remain fully loadable by `GetOperationDiff`.
3. `GetOperationDiff` / `workspace_diff` uses Git history to reconstruct before/after content and diffs for committed operations, leaving result shape and MCP schema completely unchanged.
4. Schema version 5 migration cleanly strips bodies from legacy receipts and verifies shrinkage on the live hub fixture.
5. All test suites pass cleanly with `make check` and `make web-check`.
