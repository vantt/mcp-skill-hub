# Upstream / vendored update UX patterns (research, 2026-10-04)

**Bottom line:** Copy the shape of `npm outdated` for the listing, the skills CLI/vendir approach (GitHub tree SHA for the folder) for detection, and the cruft/copier 3-way update for skills with local edits. Use the IDE pattern (badge, filter, "ignore this update") for the web UI. Status should have two dimensions: upstream change (folder tree SHA) and local change (disk digest vs recorded digest). The tools that have only one dimension either overwrite local edits silently (skills CLI, vendir) or require a clean git tree (cruft).

## 1. Package-manager `outdated` listings
- **npm outdated**: the columns are Package, Current, Wanted, Latest, Location, Depended by, plus type and homepage with `--long`. Red means an update fits your range ("update now"). Yellow means the update is outside your range, usually a major ("proceed with caution"). https://docs.npmjs.com/cli/v10/commands/npm-outdated
  - It exits 1 when anything is outdated, including with `--json`. This has been disputed for years: listing outdated packages is not an error, and the exit code breaks `--json` piping. https://github.com/npm/cli/issues/3844 , https://github.com/npm/cli/pull/3799 , https://github.com/npm/rfcs/issues/473
  - `--json` returns an object keyed by package name: `{current, wanted, latest, dependent, location}`.
- **cargo outdated**: the columns are Name, Project, Compat, Latest, Kind, Platform. `---` means no compatible version exists, and **`Removed`** means the dependency is gone upstream. `--exit-code N` is opt-in and defaults to 0. `--format json`. https://github.com/kbknapp/cargo-outdated
- **pip list --outdated**: the columns are Package, Version, Latest, Type. JSON gives `{name, version, latest_version, latest_filetype}`. It always exits 0. https://pip.pypa.io/en/stable/cli/pip_list/
- **brew outdated**: shows versions in a TTY or with `-v` (`installed < latest`). `--json=v2` separates formulae from casks. Pinned packages (`brew pin`) are left out of the list. `brew update` refreshes taps (git repos), and `HOMEBREW_AUTO_UPDATE_SECS` throttles how often the auto-refresh runs. https://docs.brew.sh/Manpage
- **Takeaways:** use a compact table showing current, target, and a delta. Color by risk, not just by "has update." Give "removed upstream" its own explicit state, as cargo does. Make the non-zero exit opt-in (cargo, cruft check), or document it clearly if it is the default (npm).

## 2. Dependabot / Renovate update PRs
- **Dependabot PR body**: release notes, changelog entries, and the commit list between versions. The compatibility score is computed from CI results in other repos. https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-pull-requests , https://arxiv.org/pdf/2206.07230
- **Scheduling**: version updates run daily, weekly, or monthly. Security updates ignore the schedule. `groups` merges several dependencies into one PR.
- **Ignore and snooze**: comment commands include `ignore this dependency`, `ignore this major|minor|patch version`, `show X ignore conditions`, `unignore`, and `recreate`. `recreate` overwrites your edits to the PR. Ignore state is stored centrally, and the docs recommend putting durable ignores in config. https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-pull-request-comment-commands
- **Renovate Dependency Dashboard**: a single issue that lists every pending update. Closing a PR unmerged moves it to "Closed/Ignored", and you re-request it with a checkbox. Approval can be required for all updates, by update type (for example majors), or per package. It also warns about deprecated or abandoned packages. https://docs.renovatebot.com/key-concepts/dashboard/
- **Merge Confidence badges**: Age, Adoption, Passing, and Confidence (Low, Neutral, High, Very High). A release must be at least 3 days old to rate High. https://docs.renovatebot.com/merge-confidence/
- **Takeaways:** the review screen should show the commit list from base to target and the per-file diff for the folder. "Ignore this version" and "ignore this source" are different actions, and the user needs a way to see and undo ignores.

## 3. IDE extension updates
- **VS Code**: the `@updates` filter in the Extensions view, an Update button on each row, and a count badge on the activity-bar icon. `extensions.autoUpdate` takes `true`, `onlyEnabledExtensions`, or `false`. `extensions.autoCheckUpdates` controls checking separately from installing. `autoUpdateDelay` defaults to 12h, a short wait after publish before auto-installing. "Install Another Version" lets you pin a version. https://code.visualstudio.com/docs/configure/extensions/extension-marketplace
- **JetBrains**: an Update or "Update All" action in Settings > Plugins, an "Update plugins automatically" toggle, and **"Manage ignored updates"**, a list of ignored versions you can restore. https://www.jetbrains.com/help/idea/managing-plugins.html
- **Claude Code plugins**: auto-update is per marketplace (source). It is on for official marketplaces and off for third-party ones. Updates go to disk, but the running session keeps its loaded version and shows "Plugin updated: X · Run /reload-plugins". The `/plugin` list includes "Last updated" and "Not used recently". There is no command to update every plugin; you update one plugin or one marketplace. https://code.claude.com/docs/en/discover-plugins
- **Takeaways:** use a count badge and a one-click filter, and keep "check" separate from "apply." Auto-apply should be a per-source opt-in and never the default for third-party sources.

## 4. Vendoring and templating tools (drift, base tracking, local edits)
| Tool | Base tracked | Upstream drift detection | Local edits on update | Check exit |
|---|---|---|---|---|
| **skills CLI** (vercel-labs/skills) | Global lock: `source, ref, skillPath, skillFolderHash` (**GitHub tree SHA of the folder**), installedAt/updatedAt. Project `skills-lock.json`: `computedHash` (sha256 of files on disk), no timestamps so merges stay clean | One Trees API call per source+ref, then compares the folder tree SHA. Falls back to `git clone` if the API is unavailable or paths moved | **Not detected; update overwrites.** Skills deleted upstream get a warning, and removal needs confirmation (skipped when non-interactive). Ambiguous relocations are skipped | No `check` command; prints "All skills are up to date" |
| **vendir** | `vendir.lock.yml`: `git.sha`, `commitTitle`, `tags` | `vendir sync` re-resolves the ref. `lazy: true` skips the fetch when config is unchanged; `--locked` replays the lock | **Overwrites** the directory except `ignorePaths`. Subfolders are handled with `includePaths` and `newRootPath` | None (diff via git) |
| **git subtree** | `git-subtree-dir`/`git-subtree-split` trailers in commits | `git fetch` of the remote | Real `git merge`, with conflict markers. `--squash` collapses history into one commit | None |
| **cruft** | `.cruft.json`: `template, commit, checkout, skip[]` | `cruft check` compares the stored commit with the template HEAD | Renders the old and new template, diffs them, applies with `git apply -3`, and falls back to `git apply --reject` (writes `*.rej`). **Requires a clean git tree.** Interactive review before apply (`--skip-apply-ask`) | **`check` exits 1 when outdated**, printing SUCCESS or FAILURE lines. Built for CI |
| **copier** | `.copier-answers.yml` `_commit` (do not hand-edit) | Compares with newer template tags | 3-way merge: regenerate from the old version, diff against the project, replay onto the new version. `--conflict inline` (default, git-style markers) or `--conflict rej` | n/a |

Sources: https://github.com/vercel-labs/skills (`src/skill-lock.ts`, `src/local-lock.ts`, `src/update.ts`), https://carvel.dev/vendir/docs/latest/vendir-lock-spec/ , https://carvel.dev/vendir/docs/latest/vendir-spec/ , https://raw.githubusercontent.com/git/git/master/contrib/subtree/git-subtree.adoc , https://cruft.github.io/cruft/ (and `cruft/_commands/update.py`, `check.py`), https://copier.readthedocs.io/en/stable/updating/

- **Takeaway:** a 3-way merge needs the *base* content. cruft and copier get it by re-rendering the old commit. We already record `commit + folder path`, so we can fetch the base folder at the recorded commit on demand, or cache it at install time. Comparing the folder tree SHA (as the skills CLI does) is the cheapest upstream check. Hashing local files against the recorded digest (as `skills-lock.json` does) is the cheapest local-edit check.

## 5. Check frequency and staleness
- **GitHub REST limits**: 60 requests/h unauthenticated, per IP, and 5,000/h with a token. A conditional request (ETag, `If-None-Match`) that returns **304 does not count** against the limit, but only when the request is authenticated. https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api , https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api
- **`git ls-remote <url> <ref>`**: returns the ref's commit SHA without cloning and uses no REST quota. It is the cheapest "did HEAD move?" probe. Only fetch the tree or compare when the SHA differs from the last one seen.
- **Grouping by source**: skills CLI makes one tree call per repo+ref for all skills from that repo, and Claude Code updates per marketplace. Check per *source*, not per skill.
- **Throttling and staleness**: Homebrew throttles auto-update with `HOMEBREW_AUTO_UPDATE_SECS`. VS Code separates check from apply and waits before auto-applying. Claude Code shows "Last updated". Store and show `last_checked_at` per source, and treat the status as unknown or stale once it is older than a TTL.

## Recommendations for our design
1. **Store a two-axis status per skill and derive the label.** The upstream axis compares the folder tree SHA at the ref HEAD with the recorded one: `same`, `changed`, or `folder-missing`. The local axis compares the disk digest with the recorded digest: `clean` or `modified`. The labels are `up-to-date`, `behind`, `modified` (local only), `diverged` (both changed), `upstream-removed`, and `unknown` (never checked or stale).
2. **Compute "behind N commits" only for display and on demand.** Use the compare API (`base...head`) limited to commits that touch the folder path. Record the folder tree SHA when a skill is installed and use it for the decision, because repo-level commits that don't touch the folder are not an update.
3. **Check cheaply, per source.** Run `git ls-remote` per repo+ref first. Only when the SHA moved, make one Trees API call (or shallow fetch) for all skills from that repo. Use ETags with a token, and fall back to `git` when there is no token or the limit is hit (as the skills CLI does).
4. **Persist `last_checked_at` and `last_seen_head` per source.** Show "checked 3h ago" in the CLI and UI. Use a default TTL (for example 24h) for implicit background checks, and an explicit `--refresh` flag or "Check now" button to force one.
5. **Model `skillhub outdated` on npm and cargo.** Columns: Skill, Source (repo@ref), Current (short commit), Latest (short commit), Behind, Local (clean/modified), Status. Color: behind+clean is green ("safe to update"), diverged is yellow, removed is red. `--json` returns an array of objects with a stable `status` enum.
6. **Exit 0 by default; opt in for CI.** Exit 0 even when updates exist. Add `--exit-code` (as cargo does), or have a `check` subcommand exit 1 when anything is behind or diverged (as `cruft check` does). Never let `--json` change the exit code; that is npm's long-standing complaint.
7. **Review update flow.** Show the commit list (base to target, filtered to the folder) and the per-file upstream diff. For `diverged` skills, also show the local diff against the base. Actions are Apply, Skip, and Ignore this version.
8. **Never overwrite local edits silently.** Unlike skills CLI and vendir, run a 3-way merge per file (base = folder at the recorded commit, ours = disk, theirs = new). Write git-style conflict markers by default and mark the skill `conflicted` until it is resolved. Offer "keep mine", "take theirs", and "abort". Stage into a temp dir and swap atomically so an aborted update leaves the skill untouched.
9. **Upstream-removed or relocated:** warn and keep the local copy. Offer "detach (make local)" or "remove", and never auto-delete in non-interactive mode (skills CLI does the same). If the same folder digest appears at a new path, suggest "relocated to X" instead of "removed".
10. **Ignore and snooze state that the user can see.** Support "ignore this upstream commit" (it resurfaces on the next upstream change) and "pin / ignore this source". Pinned or ignored skills are left out of `outdated` by default, as Homebrew does with pins. Add `--all` to include them, and a "Manage ignored updates" view (JetBrains) for undoing them.
11. **Web UI.** Add status badges on list rows. A header count chip filters to "Updates (N)", like VS Code's `@updates`. The filter offers all statuses plus "Modified locally". The sources view groups skills by repo@ref and shows last checked, HEAD commit, counts per status, and per-source "Check now" and "Update all clean" actions. Diverged skills always go through review.
12. **Auto-apply off by default.** If it is added, make it an opt-in per source and only for `behind` + `clean` skills. Add an optional minimum-age delay (VS Code waits 12h, Renovate's confidence ratings wait 3 days) so a bad upstream push does not propagate immediately. Running sessions keep their loaded snapshot until reload, as Claude Code does.

## Limitations and unresolved questions
- I did not test npm's `--json` exit behavior on the current npm version. The disputed exit-1 behavior is documented in issues, not in the npm docs.
- The Dependabot compatibility-score UI could only be confirmed from secondary sources.
- vendir's handling of local edits comes from `ignorePaths` in the spec ("preserving" files from being overwritten or deleted), not from a test run.
- Open: should the base folder be cached at install time, so 3-way merges work offline, or fetched on demand at the recorded commit? Should behind-N count all repo commits or only commits that touch the folder? I recommend folder-only.
- Open: refs that are tags. Should a tag that moves upstream count as "behind", or should we look for newer tags, copier-style?
